6.1. Create Research Project

Confirmed (outline): người dùng tạo project và nhập ngữ cảnh ban đầu; hệ thống tạo workspace và khởi tạo trạng thái bền vững.

  • Actor: Researcher; System.
  • Luồng: Researcher tạo project từ Research Projects, Dashboard hoặc Global AI Assistant → nhập tên và tối thiểu câu hỏi hoặc chủ đề nghiên cứu → System tạo Research Project (Active), Research Plan rỗng, Shared Context, Research Context phiên bản 1, Audit Event → mở Project Workspace tại Project AI Chat.
  • Kết quả: project tồn tại và khôi phục được ở mọi phiên sau. Manuscript chưa được tạo (12.1).

6.2. Research Context Gathering

Confirmed (outline): trao đổi với Orchestrator qua chat; Orchestrator xác định mục tiêu, ràng buộc, thông tin thiếu và điểm mơ hồ; hệ thống hỏi lại khi thiếu thông tin thiết yếu.

  • Luồng: Orchestrator đọc Research Context → đối chiếu với danh sách thông tin thiết yếu cố định để lập Plan (chốt — biên soạn, 30/10/2026): câu hỏi nghiên cứu, mục tiêu, loại sản phẩm đầu ra, phạm vi, ràng buộc thời gian/phương pháp, ngôn ngữ bản thảo. Orchestrator được hỏi thêm thông tin ngoài danh sách khi đề tài cần, nhưng không được coi thông tin ngoài danh sách là điều kiện bắt buộc → hỏi bổ sung bằng chat hoặc Interactive Agent Prompt information_request → ghi câu trả lời vào Research Context (phiên bản mới) và Context Item.
  • Quy tắc: Orchestrator đề xuất cập nhật Research Context (c*); thay đổi chỉ được ghi khi Researcher xác nhận, trực tiếp hoặc qua prompt. Mỗi điểm mơ hồ chưa được giải quyết được ghi thành Context Item loại assumption, hiển thị trong Plan đề xuất.
  • Kết thúc: khi đủ thông tin thiết yếu, hoặc khi Researcher yêu cầu lập Plan với giả định hiện có.

6.3. Multi-Agent Analysis

Confirmed (outline): Orchestrator giao phân tích cho Specialist Agent liên quan; agent tạo đề xuất và phát hiện có cấu trúc; Orchestrator tổng hợp phương án, bất đồng, giả định, rủi ro.

  • Thảo luận (bổ sung 01/11/2026, DEC-47): bước phân tích chạy như một phiên thảo luận (8.7): Orchestrator nêu vấn đề bằng Problem Brief (định hướng, cấu trúc Plan, phương pháp); Orchestrator và tối thiểu hai Analysis Agent đề xuất độc lập, phản biện chéo; Orchestrator tổng hợp đồng thuận, bất đồng và đánh đổi. Specialist Agent có thể được giao bước khảo sát đầu vào chạy song song (14.9). Researcher có thể bỏ qua thảo luận; khi đó Plan mang nhãn “không qua thảo luận”.
  • Luồng (bản 31/10/2026, áp dụng cho bước khảo sát đầu vào): Orchestrator tạo Workflow loại plan_proposal → giao bước phân tích cho agent phù hợp (ví dụ Discovery khảo sát nhanh hướng tài liệu, Synthesis đề xuất cấu trúc literature review, Writing đề xuất cấu trúc sản phẩm đầu ra) → mỗi Agent Run trả kết quả có cấu trúc → Orchestrator tổng hợp.
  • Quy tắc: phân tích ở bước này không tạo Trusted Reference, evidence hay claim chính thức; kết quả là Artifact Version Draft loại note đính kèm Plan đề xuất. Toàn bộ hiển thị ở Agent Activity (SCOPE-12).

6.4. Plan Proposal

Confirmed (outline): hệ thống tạo Plan nháp có phase, task, dependency, deliverable và execution label; người dùng xem, sửa, sắp xếp lại hoặc từ chối.

  • Luồng: Orchestrator tạo Plan Version Draft → System kiểm tra cấu trúc (mỗi Task có đầu ra mong đợi và acceptance criteria; dependency không có chu trình; label hợp lệ) → Researcher sửa trực tiếp hoặc yêu cầu Orchestrator sửa → Researcher trình duyệt → Plan Version Proposed.
  • Quy tắc: Orchestrator đề xuất execution label cho từng Task kèm lý do; Task cần đóng góp trí tuệ, phán đoán chuyên môn hoặc thao tác ngoài hệ thống (ví dụ thu thập dữ liệu thực nghiệm, phỏng vấn) được đề xuất Manual editor requirement (9.7).

6.5. Plan Approval

Confirmed (outline, 20.1): người dùng phê duyệt rõ ràng trước khi thực thi chính thức; phiên bản đã duyệt là baseline; thay đổi lớn cần review lại.

  • Luồng: Researcher xem Plan Version Proposed (so sánh với baseline nếu có) → duyệt (APR-01) hoặc từ chối kèm lý do → khi duyệt: version thành Approved, baseline cũ thành Superseded; System tính trạng thái Task: không còn dependency mở và đủ đầu vào → Ready, ngược lại → Blocked.
  • Thay đổi sau khi duyệt: mọi sửa đổi baseline tạo Plan Version Draft mới. Thay đổi lớn (MC-01–MC-08 ở 9.11) bắt buộc qua APR-01 đầy đủ. Thay đổi không thuộc danh sách thay đổi lớn (ví dụ chính tả, mô tả không đổi nghĩa) được duyệt nhanh trong một thao tác: Researcher xem diff và duyệt một lần; System vẫn tạo Plan Version mới và ghi phê duyệt APR-01 vào audit trail. Confirmed — PO chốt 31/10/2026 (PC-01, OQ-026).
  • Task đang chạy khi baseline đổi: tiếp tục theo version nó đã bắt đầu; khi vào In Review, System đánh dấu nếu định nghĩa Task ở baseline mới khác.

6.6. Task Selection and Readiness Check

Confirmed (outline): người dùng chọn từng Task; Orchestrator kiểm tra điều kiện; hệ thống cho phép chạy, yêu cầu bổ sung, chờ duyệt hoặc chỉ ra Task tiên quyết.

Chi tiết ở WF-02.

6.7. Task Execution

Confirmed (outline): agent thực thi Task đủ điều kiện; Task manual do người dùng kiểm soát; đầu ra lưu thành artifact có phiên bản và provenance.

  • Task Available for agent: System tạo Workflow task_execution → Orchestrator lập các bước theo loại Task → giao Specialist Agent → mỗi đầu ra lưu thành Artifact Version Draft (hoặc Evidence, Claim Draft, Change Proposal) có provenance → khi các bước xong, Task → In Review.
  • Task Manual editor requirement: theo WF-03.
  • Trong khi chạy, Researcher theo dõi và điều khiển ở Agent Activity; mọi quyết định cần thiết đi qua Interactive Agent Prompt; Task → Waiting for User khi có prompt Open chặn tiến trình.

6.8. Task Review and Acceptance

Confirmed (outline): người dùng review đầu ra theo acceptance criteria; Task được nghiệm thu, trả lại, chặn hoặc thất bại.

  • Luồng: Researcher mở Task In Review → xem đầu ra cạnh acceptance criteria và checklist → với từng artifact: chấp nhận hoặc từ chối → nghiệm thu Task (APR-03) chỉ khi mọi acceptance criteria được đánh dấu đạt và đầu ra bắt buộc có version Accepted.
  • Kết quả khác: Trả lại → Researcher ghi phản hồi và reasonCode, Task → Ready (T-13) để chạy lại với phản hồi là Context Item phạm vi task. Chặn → Task → Blocked kèm lý do và reasonCode, ví dụ phát hiện thiếu dữ liệu (T-15). Hủy → Cancelled (T-18).

6.9. Continue Research

Confirmed (outline, 20.1): Task hoàn thành mở khóa Task phụ thuộc; người dùng chọn Task tiếp theo; tiến độ, quyết định, artifact tồn tại qua các phiên.

  • Khi Task → Completed, System tính lại trạng thái Task phụ thuộc trực tiếp và thông báo Task mới Ready. Orchestrator có thể gợi ý Task nên làm tiếp nhưng không kích hoạt (Confirmed — 9.6).
  • Overview hiển thị tiến độ theo Phase và bước tiếp theo gợi ý ở mọi lần mở project.

6.10. Research Synthesis and Manuscript

Confirmed (outline): evidence và artifact được chấp nhận đi vào literature synthesis và LaTeX drafting; claim và citation truy vết được về nguồn.

Chi tiết ở WF-05 và WF-07.

6.11. Recovery and Resumption

Confirmed (outline): người dùng quay lại sau gián đoạn; hệ thống khôi phục trạng thái nhất quán gần nhất và chỉ ra quyết định đang chờ và bước tiếp theo.

Chi tiết ở WF-06.

WF-01–WF-07: workflow bắt buộc

Bảy workflow dưới đây là phạm vi bắt buộc của MVP (2.1). Mỗi workflow dùng cùng cấu trúc: actor, trigger, điều kiện trước, luồng chính, nhánh thay thế và lỗi, thay đổi trạng thái, điểm duyệt, đầu ra. Requirement chi tiết ở các mục 7–13 tham chiếu mã bước, ví dụ WF-02.S3; acceptance criteria ở mục 19.

WF-01 — Research Planning and Approval

Chuỗi bước Confirmed (outline): tạo project → cung cấp context → Orchestrator phân tích → agent con đề xuất → tổng hợp Plan → người dùng chỉnh sửa → phê duyệt → lưu phiên bản Plan chính thức.

ActorResearcher, Orchestrator, Analysis Agent (thảo luận), Specialist Agent (khảo sát), System
TriggerResearcher yêu cầu lập Plan trong Project AI Chat, hoặc yêu cầu thay đổi baseline.
Điều kiện trướcProject Active; Research Context có tối thiểu câu hỏi hoặc chủ đề; Orchestrator có Agent Model Assignment hợp lệ; không có Plan Version Draft/Proposed khác đang mở.
Luồng chính
  1. S1 Orchestrator kiểm tra thông tin thiết yếu; hỏi bổ sung nếu thiếu (6.2).
  2. S2 System tạo Workflow plan_proposal; Orchestrator mở phiên thảo luận với các Analysis Agent và có thể giao bước khảo sát cho Specialist Agent (6.3, 8.7).
  3. S3 Orchestrator tổng hợp từ Deliberation Record: phase, Task, dependency, deliverable, label đề xuất, rủi ro, giả định, các bất đồng giữa agent.
  4. S4 System tạo Plan Version Draft và kiểm tra cấu trúc (không chu trình, Task đủ trường bắt buộc).
  5. S5 Researcher xem, sửa, sắp xếp lại, thêm/xóa Task hoặc yêu cầu Orchestrator sửa; mỗi lượt sửa của agent là đề xuất cần Researcher áp dụng.
  6. S6 Researcher trình duyệt → Proposed; tạo pending action Plan approval request.
  7. S7 Researcher duyệt (APR-01) → Approved; baseline cũ → Superseded; Audit Event.
  8. S8 System tính trạng thái Task (Ready/Blocked); Overview cập nhật tiến độ và bước gợi ý.
Nhánh thay thế / lỗi
  • A1 Thiếu thông tin thiết yếu và Researcher không bổ sung: Orchestrator lập Plan với giả định ghi rõ (Context Item assumption), hiển thị nổi bật khi duyệt.
  • A2 Researcher từ chối ở S7: version → Rejected kèm lý do; Orchestrator có thể đề xuất Draft mới dựa trên lý do.
  • E1 Dependency có chu trình hoặc Task thiếu trường bắt buộc ở S4: không cho trình duyệt; chỉ rõ Task lỗi.
  • E2 Agent Run lỗi ở S2: thử lại chỉ với lỗi tạm thời: adapter gọi lại tối đa 3 lần trong cùng Agent Run (17.1), rồi Orchestrator tạo tối đa 2 Agent Run mới (ORCH-FAILURE-001); nếu vẫn lỗi, Orchestrator tổng hợp từ kết quả có được và ghi rõ phần thiếu, hoặc workflow → Failed và Researcher chọn chạy lại.
  • E3 Gián đoạn: theo WF-06; Plan Version Draft đã lưu không mất.
Điểm duyệtAPR-01 tại S7. Xác nhận cập nhật Research Context tại S1.
Đầu raPlan Version Approved (baseline), Task với trạng thái tính toán, Artifact (note) phân tích, Context Item quyết định và giả định, Audit Event.

WF-02 — Task Selection and Readiness

Chuỗi bước Confirmed (outline): chọn Task → kiểm tra Plan đã duyệt → kiểm tra dependencies → kiểm tra đầu vào và quyết định → cho phép chạy, yêu cầu bổ sung thông tin hoặc chặn Task và hướng người dùng đến công việc tiên quyết.

ActorResearcher, System (kiểm tra xác định), Orchestrator (kiểm tra ngữ nghĩa và giải thích)
TriggerResearcher chọn một Task và yêu cầu thực thi (từ Plan and Tasks hoặc Project AI Chat).
Điều kiện trướcTask thuộc baseline; trạng thái Ready, Blocked, Failed hoặc vừa được trả lại.
Luồng chính
  1. S1 System kiểm tra: có baseline Approved; Task thuộc baseline; Task không có Workflow đang hoạt động.
  2. S2 System kiểm tra dependency: mọi Task tiên quyết Completed và không mang cờ needs review.
  3. S3 System kiểm tra đầu vào khai báo: reference đã chọn và Indexed (nếu cần evidence), artifact đầu vào có version Accepted, quyết định cần thiết đã có.
  4. S4 System kiểm tra quyền và cấu hình: agent cần dùng có Agent Model Assignment với Provider Connection Valid.
  5. S5 Orchestrator kiểm tra ngữ nghĩa: đầu vào có đủ để tạo đầu ra mong đợi không; liệt kê thông tin còn thiếu.
  6. S6 System trình kết quả readiness: Đạt hoặc danh sách lý do chặn, mỗi lý do kèm hành động gợi ý (mở Task tiên quyết, bổ sung thông tin, chọn reference, cấu hình provider).
  7. S7 Nếu Đạt: Researcher xác nhận kích hoạt (APR-02) → Task → Queued → System tạo Workflow task_execution (hoặc WF-03 nếu manual).
Nhánh thay thế / lỗi
  • A1 Thiếu thông tin: Orchestrator tạo prompt information_request; trả lời xong thì chạy lại từ S3.
  • A2 Dependency chưa xong: Task → Blocked; chỉ ra Task tiên quyết và trạng thái của chúng; không cho kích hoạt.
  • A3 Researcher muốn chạy dù thiếu: không được phép bỏ qua kiểm tra; Researcher phải sửa Plan (bỏ dependency, đổi đầu vào) qua WF-01 (3.1).
  • E1 Kiểm tra ngữ nghĩa S5 lỗi do provider: hiển thị kết quả S1–S4, cho phép thử lại S5; không coi là Đạt.
Điểm duyệtAPR-02 tại S7.
Đầu raKết quả readiness lưu trong lịch sử Task; Task Queued hoặc Blocked; pending action khi cần.

WF-03 — Manual Work Enforcement

Chuỗi bước Confirmed (outline): Task có nhãn thủ công → hệ thống trình bày yêu cầu và bằng chứng cần cung cấp → người dùng thực hiện → gửi kết quả/xác nhận → kiểm tra tiêu chí nghiệm thu → mới được đánh dấu hoàn thành.

ActorResearcher, System; Orchestrator và Verification Agent chỉ hỗ trợ khi Researcher yêu cầu
TriggerTask Manual editor requirement qua WF-02 và được Researcher kích hoạt.
Điều kiện trướcReadiness Đạt.
Luồng chính
  1. S1 Task → In Progress (chủ thể: Researcher). System tạo pending action Manual work required.
  2. S2 System trình bày: mục tiêu, việc cần làm, đầu ra bắt buộc (file, văn bản, xác nhận), bằng chứng cần nộp, acceptance criteria, checklist.
  3. S3 Researcher thực hiện ngoài hoặc trong hệ thống (ví dụ sửa trực tiếp file bản thảo, tải lên dữ liệu).
  4. S4 Researcher gửi kết quả → System lưu Artifact Version loại manual_submission (actor: Researcher) → Task → In Review.
  5. S5 System kiểm tra đầu ra bắt buộc đã đủ; Researcher tự đánh giá từng acceptance criterion.
  6. S6 Researcher nghiệm thu (APR-03) → Completed.
Nhánh thay thế / lỗi
  • A1 Researcher yêu cầu agent kiểm tra kết quả (ví dụ Verification Agent kiểm tra citation): chạy như workflow phụ, đầu ra là verification_report, không thay đầu ra chính.
  • A2 Researcher yêu cầu agent làm thay: bị từ chối với giải thích; muốn đổi thì phải đổi label như một thay đổi lớn MC-06: tạo Plan Version mới, ghi lý do và duyệt APR-01 (APR-10).
  • E1 Thiếu đầu ra bắt buộc ở S5: không cho nghiệm thu; chỉ rõ phần thiếu.
Điểm duyệtAPR-03 tại S6.
Đầu raArtifact manual_submission; Task Completed; Audit Event ghi actor Researcher.

WF-04 — Reference Discovery and Trust

Chuỗi bước Confirmed (outline): tìm trên Google Scholar → xem kết quả → chọn tài liệu → kiểm tra metadata → yêu cầu duyệt qua Interactive Agent Prompt → nhập thư viện → indexing → cho phép sử dụng làm nguồn tin cậy theo chính sách.

ActorResearcher, Discovery Agent, Reference Processing Agent, System
TriggerResearcher tìm ở Discover, hoặc một Task tìm tài liệu được thực thi.
Điều kiện trướcDiscovery Agent và Reference Processing Agent có kết nối provider hợp lệ; có ít nhất một nguồn tìm kiếm khả dụng: Google Scholar qua dịch vụ trung gian theo hợp đồng (SCOPE-06, OQ-081), hoặc, nếu Google Scholar không khả thi, một nguồn có API hợp lệ (ví dụ OpenAlex hoặc Semantic Scholar) qua interface nguồn 10.9 (OQ-006). Confirmed — PO chốt 31/10/2026 (PC-01, OQ-006, OQ-081).
Luồng chính
  1. S1 Discovery Agent chạy truy vấn (query, tiêu đề, tác giả, từ khóa) → Discovered Result New.
  2. S2 Researcher xem kết quả; chọn (Selected) hoặc loại (Rejected) từng kết quả hoặc theo nhóm.
  3. S3 Reference Processing Agent chuẩn hóa metadata, phát hiện trùng với Trusted Library, tạo Reference Pending Approval.
  4. S4 System tạo Interactive Agent Prompt approval (hoặc edit_and_approve khi metadata cần sửa) cho từng reference hoặc theo lô trong một prompt; reference có cảnh báo trùng không nằm trong lô mà được xử lý riêng (A1). Confirmed — PO chốt 31/10/2026 (PC-01, OQ-039).
  5. S5 Researcher duyệt (APR-04) → Reference Trusted; Discovered Result → Imported. Khi duyệt theo lô, audit trail vẫn ghi phê duyệt riêng cho từng reference.
  6. S6 Nếu có nội dung truy cập hợp lệ: System index (indexing Queued → Indexing → Indexed) vào vector database. Nếu không: Unavailable, reference vẫn dùng được cho citation nhưng không cho evidence.
  7. S7 Nếu workflow chạy trong một Task: reference được đề xuất thêm vào Project Reference Selection; Researcher xác nhận.
Nhánh thay thế / lỗi
  • A1 Trùng lặp: Reference Processing Agent đề xuất gộp vào reference sẵn có; Researcher chọn gộp hoặc giữ riêng cho từng reference (không duyệt theo lô).
  • A2 Researcher từ chối ở S5: Reference → Rejected; không dùng được ở đâu.
  • A3 Nhập thủ công: Researcher nhập DOI, BibTeX hoặc tải lên PDF (chỉ PDF có lớp văn bản, tối đa 50 MB/file, OQ-050) thay cho S1–S2; reference đi tiếp từ S3 (chuẩn hóa metadata, kiểm tra trùng, Pending Approval) và qua APR-04 như luồng chính (10.4). Confirmed — PO chốt 31/10/2026 (PC-01, OQ-008).
  • E1 Google Scholar (qua dịch vụ trung gian) không phản hồi, bị giới hạn hoặc chặn: báo lỗi rõ ràng, không thử vượt giới hạn (OOS-06); Researcher dùng luồng nhập do người dùng hỗ trợ (A3, OQ-081) hoặc nguồn API thay thế qua interface 10.9 nếu được dùng (OQ-006).
  • E2 Indexing thất bại: indexing Failed, thông báo; Researcher có thể thử lại hoặc cung cấp file khác.
Điểm duyệtAPR-04 tại S5; xác nhận thêm vào project tại S7.
Đầu raTrusted Reference trong Trusted Library; Source Document đã index (nếu có); Project Reference Selection (nếu trong Task).

WF-05 — Evidence-to-Manuscript

Chuỗi bước Confirmed (outline): truy xuất bằng chứng → liên kết claim với nguồn → đánh giá mức độ hỗ trợ → tổng hợp → người dùng duyệt → tạo hoặc sửa LaTeX → kiểm tra citation → compile → review PDF.

ActorResearcher, Evidence Retrieval, Synthesis, Verification, Writing Agent, System
TriggerTask tổng hợp hoặc viết được thực thi.
Điều kiện trướcProject có Trusted Reference được chọn và Indexed; với bước viết: Manuscript đã khởi tạo.
Luồng chính
  1. S1 Evidence Retrieval Agent truy xuất đoạn liên quan từ vector database (RAG) → Evidence Active.
  2. S2 Synthesis Agent tạo claim và liên kết evidence (supports/contradicts) → Claim Draft; bản tổng hợp → Artifact Version Draft.
  3. S3 Verification Agent đánh giá mức hỗ trợ từng claim và kiểm tra trích dẫn khớp nguồn → Supported / Partially Supported / Unsupported / Conflicting.
  4. S4 Researcher review trong Evidence Inspector: chấp nhận, sửa, từ chối claim (APR-06); chấp nhận bản tổng hợp.
  5. S5 Writing Agent tạo Change Proposal (diff LaTeX) chỉ từ claim và artifact Accepted; citation dùng BibTeX key của Trusted Reference.
  6. S6 Verification Agent kiểm tra citation trong diff: mọi key phân giải được; câu có citation khớp claim/evidence.
  7. S7 Researcher xem diff kèm kết quả kiểm tra; chấp nhận (APR-05) → Manuscript Revision mới.
  8. S8 System compile → Build Succeeded → Researcher xem PDF.
Nhánh thay thế / lỗi
  • A1 Evidence mâu thuẫn: claim → Conflicting; bản tổng hợp phải trình bày cả hai phía (11.7).
  • A2 Không đủ evidence: claim giữ Unsupported và nhãn hiển thị; Orchestrator có thể gợi ý Task tìm thêm tài liệu (không tự chạy).
  • A3 File đã đổi trước khi chấp nhận diff: Change Proposal → Outdated; Writing Agent có thể tạo lại trên revision mới.
  • E1 Citation không phân giải ở S6: diff được đánh dấu lỗi; không cho chấp nhận đến khi sửa (KPI-02).
  • E2 Build lỗi ở S8: Build Failed; log và lỗi được diễn giải dễ hiểu cho người dùng LaTeX cơ bản (OQ-002, 12.7).
Điểm duyệtAPR-06 tại S4; APR-05 tại S7.
Đầu raEvidence; Claim Accepted có mức hỗ trợ; bản tổng hợp Accepted; Manuscript Revision; Build và PDF.

WF-06 — Long-Running Workflow Recovery

Chuỗi bước Confirmed (outline): Task đang chạy hoặc chờ → phiên làm việc kết thúc/agent lỗi → lưu checkpoint → người dùng quay lại → khôi phục trạng thái → kiểm tra kết quả chưa hoàn tất → tiếp tục hoặc yêu cầu chạy lại có kiểm soát.

ActorSystem, Researcher, Orchestrator
TriggerWorkflow dừng ngoài ý muốn (mất phiên, lỗi hạ tầng, lỗi provider kéo dài), hoặc Researcher quay lại khi có workflow Waiting for User/Paused.
Điều kiện trướcWorkflow có ít nhất một checkpoint.
Luồng chính
  1. S1 System lưu checkpoint sau mỗi bước hoàn tất và trước mỗi điểm chờ người dùng.
  2. S2 Khi phát hiện dừng ngoài ý muốn: Workflow → Interrupted; Task → Waiting for User (T-08); Agent Run đang chạy → Failed (lý do: interrupted); kết quả chưa hoàn tất không được ghi.
  3. S3 Researcher quay lại: Dashboard và Overview hiển thị workflow bị gián đoạn, prompt đang chờ và bước tiếp theo.
  4. S4 System khôi phục trạng thái tại checkpoint gần nhất; liệt kê bước đã xong, bước dở dang, đầu ra đã lưu.
  5. S5 System tạo Recovery decision: tiếp tục từ bước dở dang, chạy lại bước (Agent Run mới), hoặc hủy workflow.
  6. S6 Researcher chọn → Workflow → Running hoặc Cancelled; Task cập nhật tương ứng.
Nhánh thay thế / lỗi
  • A1 Workflow chỉ đang Waiting for User (không lỗi): không cần Recovery decision; chỉ hiển thị lại prompt.
  • A2 Baseline hoặc đầu vào đã thay đổi trong lúc gián đoạn: System cảnh báo trước khi tiếp tục; Researcher có thể chọn chạy lại từ đầu.
  • E1 Checkpoint không nhất quán: dùng checkpoint trước đó; ghi Audit Event; báo Researcher phần bị mất.
Điểm duyệtRecovery decision tại S5. System không tự chạy lại bước có tác động (gọi provider, ghi dữ liệu) khi chưa có xác nhận.
Đầu raWorkflow tiếp tục hoặc kết thúc có kiểm soát; không mất kết quả đã hoàn tất (KPI-03 ≥ 99%).

WF-07 — Diagram Generation

Chuỗi bước Confirmed (outline): Task yêu cầu sơ đồ → cung cấp context và loại sơ đồ → Diagram Agent tạo Mermaid/UML → validate cú pháp → preview → người dùng review → lưu artifact có thể chỉnh sửa → tích hợp vào báo cáo khi được chấp nhận.

ActorResearcher, Diagram Agent, System
TriggerTask cần sơ đồ được thực thi, hoặc Researcher yêu cầu trong Project AI Chat với active task.
Điều kiện trướcDiagram Agent có kết nối provider hợp lệ.
Luồng chính
  1. S1 Orchestrator lắp ráp context (yêu cầu Task, artifact accepted liên quan) và loại sơ đồ (13.2).
  2. S2 Diagram Agent tạo mã nguồn Mermaid (MVP chỉ hỗ trợ Mermaid).
  3. S3 System kiểm tra cú pháp và render preview.
  4. S4 Lưu Artifact Version Draft loại diagram (nguồn + preview).
  5. S5 Researcher review; sửa nguồn trực tiếp hoặc yêu cầu agent sửa (version mới).
  6. S6 Researcher chấp nhận (APR-07) → Accepted.
  7. S7 Nếu cần đưa vào bản thảo: tạo Change Proposal thêm file hình và lệnh chèn; theo APR-05.
Nhánh thay thế / lỗi
  • E1 Lỗi cú pháp ở S3: Diagram Agent tự sửa trong giới hạn thử lại; nếu vẫn lỗi, lưu Draft kèm lỗi để Researcher sửa tay.
  • E2 Render lỗi dù cú pháp đúng: báo lỗi render, vẫn lưu nguồn.
Điểm duyệtAPR-07 tại S6; APR-05 tại S7.
Đầu raDiagram artifact có nguồn chỉnh sửa được, preview, version, Task liên quan.
