Architecture Design · Section 3

3. System Context and Services

Trạng thái: Đề xuất (Assumption) — bản 0.2 theo chỉ đạo ngày 31/10/2026 (tách service, NestJS + Python) · Cơ sở: PRD 3, 5, 8, 14, 17; ADR-17–ADR-23

Backend chia thành các service độc lập để nhiều nhóm code song song mà không chạm luồng của nhau: mỗi service sở hữu một nhóm entity, một database riêng và một hợp đồng Swagger riêng. Service xử lý hệ thống viết bằng TypeScript/NestJS; service agent core và xử lý tri thức (PDF, embedding, truy xuất) viết bằng Python. Mục này mô tả ngữ cảnh, danh sách service, ranh giới dữ liệu, cách giao tiếp và cấu trúc monorepo.

3.5. Giao tiếp giữa service

KiểuDùng khiCơ chế
REST đồng bộCần câu trả lời ngay: gateway → service; readiness check đọc dữ liệu service khác; agent-core đọc context và gọi toolHTTP nội bộ, JSON, theo OpenAPI nội bộ; token service (10.4); timeout 2 s mặc định, không retry lệnh ghi trừ khi có Idempotency-Key
Sự kiện bất đồng bộThông báo một việc đã xảy ra: task.activated, reference.status_changed.revoked, project.lifecycle_changed.deleted…Outbox của service nguồn → relay → RabbitMQ topic exchange sires.events; consumer idempotent bằng bảng inbox (ADR-19)
Lệnh bất đồng bộ (job)Việc dài cần một worker nhận: chạy Agent Run, index tài liệu, build LaTeXQueue riêng: agent.run, knowledge.index, sandbox.build; ack thủ công, prefetch giới hạn; trạng thái thật nằm ở DB của service gửi lệnh

Không service nào đọc database của service khác. Không có giao dịch phân tán: chuỗi thay đổi xuyên service là saga có idempotency key, mỗi bước nguyên tử trong service của nó (mục 5.8, 6.4).

3.6. Quy tắc cho người viết service

  1. Swagger trước, code sau. Thêm hoặc đổi endpoint: sửa OpenAPI (công khai hoặc nội bộ) và AsyncAPI trước; CI kiểm tra code khớp spec (ADR-14).
  2. Một entity, một chủ. Không tạo bảng chứa entity của service khác; cần dữ liệu thì gọi API hoặc giữ bản sao chỉ đọc từ sự kiện, ghi rõ trong README của service.
  3. Ghi = trạng thái + audit + outbox trong một giao dịch, dùng thư viện chung libs/ts/platform (hoặc sires_common).
  4. Consumer idempotent theo event id (bảng inbox); xử lý được sự kiện đến trùng hoặc lệch thứ tự.
  5. Kiểm tra quyền ở service sở hữu, kể cả khi được gọi từ gateway hay agent-core; không tin service gọi đã kiểm tra.
  6. Đổi phá vỡ hợp đồng nội bộ hoặc sự kiện: thêm phiên bản mới, giữ bản cũ tới khi mọi consumer chuyển xong.
  7. Chỉ agent-core và knowledge import SDK provider; chỉ hai service này có quyền giải mã API key.
