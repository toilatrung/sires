4. Runtime Flows

Trạng thái: Đề xuất (Assumption) — bản 0.2 theo kiến trúc nhiều service · Cơ sở: PRD 6 (WF-01–WF-07), 8, 9, 10, 11, 12, 13, 14; API 0.1.0-mvp

Mỗi luồng F-NN mô tả service nào làm gì theo thứ tự. Hành vi và trạng thái theo PRD; mục này thêm phần service, giao dịch, message và sự kiện. Ký hiệu: [TX:svc] = một giao dịch trong database của service svc gồm thay đổi trạng thái + Audit Event + bản ghi outbox (6.4); evt:x = sự kiện x trên exchange sires.events; cmd:q = message lệnh vào queue q; REST = gọi HTTP nội bộ theo OpenAPI nội bộ.

F-01. Đăng nhập qua eTroy OIDC

INT-OIDC-001–004, NFR-AUTH-001 · ADR-09

  1. web gọi GET /api/v1/auth/login; gateway tạo state, nonce, code_verifier (PKCE), lưu ở cookie tiền-phiên (HttpOnly, 10 phút), redirect tới authorization endpoint của eTroy (discovery document được cache).
  2. Người dùng xác thực ở eTroy; eTroy redirect về /api/v1/auth/callback.
  3. gateway kiểm tra state, đổi code lấy token, kiểm tra chữ ký ID token qua JWKS, iss, aud, exp, nonce.
  4. gateway gọi REST identity POST /internal/accounts/resolve với (iss, sub, họ tên, email): [TX:identity] tìm hoặc tạo Account + Profile, Audit Event đăng nhập.
  5. [TX:gateway] tạo phiên server-side (token mã hóa, hạn theo token); trả cookie sires_session và CSRF token.
  6. Mỗi request: gateway nạp phiên, làm mới token khi cần (SPK-02), rồi ký token nội bộ ngắn hạn (ADR-20) mang account_id, actor Researcher để gọi service phía sau. Không làm mới được → 401 session_expired.
  7. eTroy không phản hồi: 503 idp_unavailable; phiên đang có không bị ảnh hưởng vì kiểm tra phiên không gọi eTroy (INT-OIDC-004).

F-02. Lệnh ghi chuẩn

NFR-AUTHZ-001, NFR-DUR-001, DATA-IDEMP-001, DATA-CONC-001, CTX-CONSISTENCY-003

  1. gateway: phiên hợp lệ, CSRF token khớp, rate limit; định tuyến theo đường dẫn tới service sở hữu, kèm token nội bộ và traceparent.
  2. Service sở hữu (pipeline chung trong libs/ts/platform): kiểm tra token nội bộ → idempotency (Idempotency-Key + hash nội dung) → mở giao dịch, SET LOCAL app.account_id → nạp entity trong phạm vi tài khoản (không thấy → 404) → If-Match so rowVersion (412) → state machine kiểm tra trạng thái, actor, APR, điều kiện.
  3. [TX:svc] entity (tăng rowVersion), Audit Event và sự kiện domain vào outbox, bản ghi idempotency.
  4. Trả lời sau commit. Tác vụ dài: 202 + tham chiếu Workflow. Việc tiếp theo ở service khác phát sinh từ sự kiện trong outbox, không gọi đồng bộ trong request.
  5. Outbox relay của service đẩy sự kiện lên RabbitMQ; audit, gateway (SSE) và các consumer liên quan nhận.

F-03. Realtime qua SSE

NFR-PERF-003 (≤ 5 s), OQ-033, SCOPE-12 · ADR-07

  1. web mở GET /api/v1/events (một kết nối mỗi tab).
  2. gateway có một consumer trên sires.events (binding theo các loại sự kiện hiển thị được); mỗi sự kiện được ghi vào log sự kiện của gateway (giữ 24 giờ, khóa theo tài khoản và thứ tự nhận) rồi đẩy tới kết nối SSE của đúng tài khoản trên mọi pod gateway (mỗi pod có queue riêng, tự xóa khi pod dừng).
  3. Nối lại với Last-Event-ID: gateway phát lại từ log sự kiện; quá 24 giờ → sự kiện resync, web tải lại dữ liệu.
  4. Chat stream dùng exchange sires.stream (không bền, không ghi log): agent-core phát delta, gateway chuyển thành SSE chat.delta.
  5. Heartbeat SSE mỗi 15 giây.

F-04. Chat với Orchestrator

PROJ-CHAT, ORCH-INTENT, NFR-PERF-005, OQ-064

  1. web POST /conversations/{conversationId}/messages → workspace [TX:workspace] lưu Message + evt:message.posted; trả 202. Trạng thái “đang xử lý” hiển thị ngay.
  2. orchestration nhận sự kiện, [TX:orchestration] tạo Workflow loại chat-turn một bước, cmd:agent.run.
  3. agent-core chạy Agent Run của Orchestrator (F-07), lớp context 7 = tóm tắt cuốn chiếu + 20 tin gần nhất (đọc từ workspace qua REST); stream delta qua sires.stream.
  4. Kết thúc: orchestration nhận kết quả, gọi REST workspace ghi Message của Orchestrator (idempotency key = agentRunId), cập nhật Context Item summary trong DB của mình. Ý định có tác động (tạo Plan, mở prompt…) chuyển thành workflow hoặc prompt, không thực hiện trực tiếp.

F-05. Lập và duyệt Plan

WF-01, PLAN-GENERATE, PLAN-APPROVAL, APR-01, DEC-28

  1. Researcher yêu cầu lập Plan → planning kiểm tra sáu trường thiết yếu của Research Context (REST workspace); thiếu thì yêu cầu orchestration mở prompt information_request.
  2. planning [TX:planning] evt:plan.generation_requested → orchestration tạo Workflow plan_proposal, cmd:agent.run.
  3. agent-core trả PlanVersion đề xuất (structured output) → orchestration gọi REST planning POST /internal/projects/{projectId}/plan/versions (idempotency key = agentRunId); planning kiểm tra cấu trúc (18.5: DAG không chu trình, mọi Task có acceptance criteria) rồi ghi Draft.
  4. orchestration mở prompt approval; Workflow → Waiting for User.
  5. Researcher duyệt (POST …/plan/versions/{id}/approve, APR-01) → [TX:planning] PlanVersion Approved, baseline cũ Superseded, Task cập nhật, phân tích ảnh hưởng (9.11), ApprovalRecord, Audit Event, evt:plan_version.status_changed.approved → orchestration đóng prompt và kết thúc workflow.

F-06. Kích hoạt Task và thực thi workflow

WF-02, WF-03, TASK-READINESS, TASK-TRIGGER, CTX-CONSISTENCY-001, T-05/T-06

  1. Researcher bấm kích hoạt (POST …/tasks/{taskId}/activate, APR-02, có Idempotency-Key) → planning.
  2. planning chạy phần xác định của readiness (RC-01–RC-09, ≤ 2 s): dữ liệu của mình + REST song song tới identity (Agent Model Assignment, Provider Connection Valid), library (reference bắt buộc đã Trusted), research (artifact đầu vào Accepted). Không đạt → trả kết quả kiểm tra.
  3. [TX:planning] khóa hàng Task; Task → Queued (T-05); evt:task.activated (kèm activationId).
  4. orchestration nhận sự kiện: [TX:orchestration] tạo Workflow task_execution (ràng buộc duy nhất “một workflow hoạt động mỗi Task” chặn trùng) và bước plan_next; evt:workflow.created → planning ghi Task.activeWorkflowId.
  5. Bước đầu bắt đầu chạy → evt:workflow.status_changed.running → planning chuyển Task → In Progress (T-06). Hệ thống chạm giới hạn tải → Task giữ Queued và hiển thị vị trí chờ.
  6. Task Manual editor requirement: planning chuyển In Progress, không tạo workflow agent (WF-03).
  7. Engine lặp: Orchestrator lập bước → Agent Run (F-07) → checkpoint → bước tiếp, cho đến khi đủ đầu ra; evt:workflow.status_changed.succeeded → planning chuyển Task → In Review, workspace tạo PendingAction nghiệm thu (APR-03).

F-07. Vòng đời một Agent Run

CTX-ROUTING-001, CTX-ASSEMBLY-001, CTX-REGISTRY-001/002, INT-PROVIDER-003/006, NFR-USAGE-001

  1. Giao việc: orchestration [TX:orchestration] tạo AgentRun Pending, gán step.currentAgentRunId, cmd:agent.run (gồm agentRunId, agent, bước, inputRefs, token nội bộ có phạm vi agent).
  2. Nhận việc: agent-core lấy message, bắt tay POST /internal/agent-runs/{agentRunId}/start ở orchestration và gửi heartbeat 30 s trong suốt Agent Run.
  3. Kiểm tra phạm vi: orchestration đã kiểm tra agent được phép với inputRefs trước khi giao (PRD 3.3); service sở hữu dữ liệu kiểm tra lại phạm vi trong token khi agent-core đọc.
  4. Lắp ráp context: Context Assembler (agent-core) gọi song song API “context bundle” của service liên quan (planning, orchestration/Context Item, research, workspace, manuscript), truy xuất evidence qua knowledge; ước lượng token, cắt từ lớp thấp, tạo context manifest.
  5. Gọi model: Model Gateway lấy ciphertext API key từ identity (REST nội bộ), giải mã bằng KMS trong bộ nhớ, gọi provider; vòng tool calling (tool là API đọc của service, kiểm tra quyền theo token); thử lại tạm thời ≤ 3, sửa định dạng ≤ 2.
  6. Kiểm tra đầu ra: validate schema; kiểm tra tất định (tham chiếu nằm trong manifest, quote có thật — 7.5).
  7. Trả kết quả: agent-core gửi REST POST /internal/agent-runs/{id}/result tới orchestration (manifest, structured output, usage, attempts, phiên bản), rồi ack message. Toàn văn debug (nếu bật) mã hóa và ghi object storage.
  8. Áp dụng đầu ra (saga): orchestration khóa hàng workflow, kiểm tra Workflow còn Running và run là run hiện hành (không → discarded); gọi REST service sở hữu để ghi đầu ra Draft kèm provenance (idempotency key = agentRunId:chỉ số đầu ra); khi mọi ghi được xác nhận: [TX:orchestration] AgentRun Succeeded, Step Succeeded, Checkpoint, evt:agent_run.status_changed.succeeded.

F-08. Prompt và phê duyệt

PROMPT-LIFECYCLE, PROMPT-APPROVAL, CTX-CONSISTENCY-003, OQ-023

  1. Đầu ra yêu cầu người dùng → [TX:orchestration] tạo InteractiveAgentPrompt (gắn objectType, objectId, objectVersion), Workflow → Waiting for User; evt:prompt.status_changed.open → workspace tạo PendingAction, gateway đẩy SSE.
  2. Researcher trả lời POST /prompts/{promptId}/response (idempotent) → orchestration.
  3. Prompt có APR: orchestration gọi REST endpoint phê duyệt của service sở hữu đối tượng với token actor Researcher (lấy từ phiên của request này) và If-Match = objectVersion. Lệch phiên bản → prompt Cancelled, Orchestrator tạo prompt mới.
  4. Phê duyệt thành công → [TX:orchestration] Prompt Answered, Context Item decision, Workflow → Running, cmd:agent.run cho bước tiếp; evt:prompt.status_changed.answered → workspace đóng PendingAction.
  5. Prompt Expired khi project lưu trữ (evt:project.lifecycle_changed.archived), Cancelled khi workflow hủy.

F-09. Discovery, nhập và index reference

WF-04, DISC-*, LIB-IMPORT, LIB-APPROVAL (APR-04), INT-SCHOLAR, INT-DOC, DEC-19–21, DEC-30–31

  1. Discovery Agent (agent-core) gọi tool search_sources = REST library; library gọi source adapter qua rate limiter, chuẩn hóa theo schema 17.6, ghi DiscoveredResult New.
  2. Dịch vụ không trả kết quả: library trả lý do; web đề nghị nhập thủ công DOI / BibTeX/RIS / PDF (library xử lý).
  3. Reference Processing Agent chuẩn hóa metadata, phát hiện trùng; library ghi Reference Pending Approval; orchestration mở prompt duyệt theo lô (tối đa 50), mục trùng tách riêng.
  4. Duyệt (APR-04) → [TX:library] mỗi Reference một ApprovalRecord → Trusted, sinh bibtexKey; evt:reference.status_changed.trusted.
  5. knowledge nhận sự kiện (có file hoặc nội dung truy cập mở) → cmd:knowledge.index nội bộ → trích xuất, chunk, embedding (key OpenAI/Gemini của người dùng) → [TX:knowledge] SourceDocument, Chunk, vector; evt:reference.indexing_status_changed.indexed → library cập nhật indexingStatus. Chi tiết ở mục 7.

F-10. Evidence, synthesis và kiểm chứng

WF-05 S1–S4, EVID-RETRIEVAL, CLAIM-*, SYN-*, DEC-32, DEC-38

  1. Orchestrator lập bước: Evidence Retrieval → Synthesis → Verification (truy xuất độc lập có thể song song, OQ-032).
  2. Evidence Retrieval Agent gọi tool retrieve_evidence = REST knowledge. Phạm vi (tài khoản + reference Active ∩ Trusted ∩ Indexed của project) do knowledge tự tính từ bản sao chỉ đọc nhận qua sự kiện của library, không nhận từ model. Kết quả được orchestration ghi vào research thành Evidence Active kèm vị trí.
  3. Synthesis Agent tạo Claim Draft + ClaimEvidenceLink + ArtifactVersion synthesis Draft → ghi vào research (research kiểm tra mọi evidenceId tồn tại).
  4. Verification Agent (có thể khác provider/model) đánh giá từng claim với bản chụp VerificationThresholds (REST identity) → research ghi VerificationResult.
  5. Task → In Review; Researcher chấp nhận claim/artifact (APR-06) ở research; KPI-01 cập nhật.

F-11. Change Proposal, build và sơ đồ

WF-05 S5+, WF-07, MS-DIFF, MS-BIB, MS-BUILD, DIAG-*, APR-05, APR-07, KPI-02

  1. Writing Agent tạo ChangeProposal → manuscript ghi (theo baseRevisionId).
  2. Cổng citation (manuscript, tất định): trích mọi key \cite*; mỗi key phải có BibliographyEntry gắn Reference Trusted (bản sao chỉ đọc trạng thái reference từ sự kiện library). Thiếu → chặn chấp nhận.
  3. Researcher chấp nhận nguyên khối (APR-05) → [TX:manuscript] base lệch → Outdated; khớp → ManuscriptRevision mới, sinh lại references.bib.
  4. Build: [TX:manuscript] Build Queued, cmd:sandbox.build → sandbox-runner chạy latexmk trong sandbox (120 s / 2 GB, không mạng), tải log/PDF lên object storage, trả kết quả qua REST manuscript → Build kết thúc, issues song ngữ.
  5. Sơ đồ (WF-07): Diagram Agent gọi tool validate_mermaid/render_mermaid = REST research → research gửi cmd:sandbox.build ưu tiên cao và chờ kết quả → SVG preview. Chấp nhận (APR-07) ở research → Writing Agent tạo ChangeProposal đưa PDF vector (hoặc PNG 300 dpi) vào figures/.

F-12. Gián đoạn và khôi phục

WF-06, CTX-RECOVERY-001, NFR-REC-001/002, KPI-03

  1. agent-core gửi heartbeat 30 s cho Agent Run đang chạy (REST orchestration, cập nhật workflow.heartbeatAt).
  2. Sweeper của orchestration (mỗi 10 s, 5.4) tìm Workflow Running có heartbeatAt < now − 110 s (phát hiện ≤ 2 phút) → [TX:orchestration] Workflow Interrupted, AgentRun Failed (interrupted), evt:workflow.status_changed.interrupted → workspace tạo PendingAction Recovery decision và Notification.
  3. Không có message agent.run nào được gửi cho workflow Interrupted (NFR-REC-002). Message cũ còn trong queue (pod agent-core chết trước khi ack, RabbitMQ giao lại) bị agent-core bỏ qua vì orchestration trả 409 khi báo started cho run không còn hiện hành.
  4. Researcher mở workflow: orchestration nạp checkpoint nhất quán gần nhất, liệt kê bước xong/dở, đầu ra đã lưu.
  5. Researcher chọn tiếp tục / chạy lại bước / hủy (POST /workflows/{workflowId}/recovery-decision) → [TX:orchestration] Running + AgentRun mới + cmd:agent.run, hoặc Cancelled.
  6. Kết quả muộn của run cũ bị từ chối ở bước 8 của F-07 → discarded.
