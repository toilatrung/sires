8. Model Gateway and Integrations

Trạng thái: bản 0.2 — ADR-08, ADR-09 Accepted; Model Gateway thuộc agent-core (Python), OIDC thuộc gateway (NestJS), source adapter thuộc library (NestJS) · Cơ sở: PRD 8.6, 17; DEC-19, DEC-23, DEC-26; ASM-01–03, ASM-10, ASM-13; ADR-08, ADR-09

Bài toán: ba provider khác nhau về tool calling, structured output, giới hạn context, mã lỗi và báo cáo usage (RISK-04); người dùng tự cấp key và có thể trỏ base URL tới proxy hoặc model tự host tương thích (DEC-23); nguồn học thuật không có API chính thức (RISK-01). Phương án: mọi phụ thuộc ngoài đứng sau một port có hợp đồng chuẩn hóa; adapter chịu trách nhiệm dịch qua lại; phần còn lại của hệ thống không biết provider nào đang chạy.

8.1. Interface Model Gateway

class ModelGateway(Protocol):
    async def generate(self, req: ModelRequest, conn: ProviderConnectionRef) -> ModelResponse: ...
    async def stream(self, req: ModelRequest, conn: ProviderConnectionRef) -> AsyncIterator[StreamEvent]: ...
    async def embed(self, texts: list[str], model: str, conn: ProviderConnectionRef) -> EmbeddingResult: ...
    async def list_models(self, conn: ProviderConnectionRef) -> list[ModelInfo]: ...      # kiểm tra kết nối

ModelRequest:  model, messages[system|user|assistant|tool_result], tools[], output_schema (JSON Schema),
               stream: bool, max_output_tokens, metadata{agentRunId, traceparent}
ModelResponse: text, tool_calls[{id, name, arguments}], structured (đã validate), stop_reason,
               usage{input_tokens, output_tokens, calls, extra} | "no_data", attempts, adapter_version
Lỗi:           GatewayError(code ∈ bộ mã chuẩn 8.6, retryable: bool, retry_after?)
  • ProviderConnectionRef chỉ mang id; adapter lấy ciphertext từ identity (GET /internal/provider-connections/{id}/secret, chỉ agent-core và knowledge được gọi), giải mã bằng KMS ngay trước lời gọi, giữ key trong biến cục bộ và không truyền ra ngoài (NFR-SECRETS-001).
  • Không có tham số nâng cao (temperature…) do người dùng chỉnh (OQ-015); giá trị mặc định do định nghĩa agent đặt, ghi trong phiên bản agent.
  • Vòng tool calling (model gọi tool → agent-core gọi API đọc của service sở hữu → trả kết quả) nằm trong một Agent Run; có thể hiện thực bằng framework agent (ADR-08), tối đa 8 vòng mỗi Agent Run (cấu hình theo agent).

8.3. Danh mục capability

  • Bảng model_catalog do identity duy trì (agent-core đọc qua API): provider, model_pattern, tool_calling, structured_output, streaming, context_window, max_output, pdf_input, image_input, embedding_dim, pricing?. Nạp từ file cấu hình trong repo, cập nhật qua deploy.
  • Khi “kiểm tra kết nối”, adapter liệt kê model của endpoint; model khớp danh mục được gắn capability; model không có trong danh mục (thường gặp với proxy/tự host) được đánh dấu chưa xác định và người dùng phải xác nhận; agent cần capability bắt buộc không gán được vào model chưa xác định.
  • Giá (để hiển thị chi phí ước tính, NFR-USAGE-003) là tùy chọn; thiếu giá thì chỉ hiển thị token.

8.5. Structured output và sửa định dạng

  1. Schema đầu ra là model Pydantic của agent; JSON Schema sinh tự động, đã đơn giản hóa về tập con chung mà cả ba provider chấp nhận (không oneOf phức tạp, có additionalProperties: false). Bộ test schema chạy trên cả ba adapter (SPK-01).
  2. Phản hồi được parse và validate bằng Pydantic ở Gateway, không tin cờ “đã đúng schema” của provider.
  3. Không hợp lệ: gửi lại một lượt kèm lỗi validate ngắn gọn, yêu cầu sửa; tối đa 2 lượt (INT-PROVIDER-003); vẫn lỗi → invalid_response.
  4. Sau validate cú pháp, System còn kiểm tra ngữ nghĩa (tham chiếu tồn tại, trong phạm vi, quote có thật — 7.5). Lỗi ngữ nghĩa không làm lại lời gọi tự động; mục đó bị loại hoặc bước Failed tùy agent.

8.6. Streaming, usage, giới hạn tốc độ

  • Streaming chỉ dùng cho câu trả lời chat của Orchestrator (NFR-PERF-005); Agent Activity cập nhật theo sự kiện, không stream token (OQ-033).
  • Usage: adapter chuẩn hóa token vào/ra và số lời gọi (cộng dồn qua thử lại và vòng tool); provider không trả usage → "no_data", không ước tính (NFR-USAGE-001, ASM-10).
  • Giới hạn đồng thời theo Provider Connection: semaphore phân tán trong agent-core (bảng đếm trong database nhỏ của agent-core, mặc định 4 lời gọi đồng thời mỗi kết nối) để workflow song song của một người dùng không tự gây 429 cho chính họ.

8.8. eTroy OIDC

  • gateway (thư viện openid-client) là Relying Party kiểu confidential client, luồng authorization code + PKCE (S256), scope openid profile email (+ offline_access nếu eTroy hỗ trợ refresh token). Discovery document và JWKS cache theo Cache-Control, làm mới khi gặp kid lạ.
  • Liên kết tài khoản theo (iss, sub), không theo email (INT-OIDC-002, RISK-10).
  • Phiên SIRes lưu server-side: id phiên ngẫu nhiên 256 bit trong cookie; bảng phiên chứa access/refresh token mã hóa, hạn, thời điểm hoạt động cuối. Hạn phiên không vượt hạn token mà eTroy cho phép làm mới (INT-OIDC-003).
  • Đăng xuất: xóa phiên SIRes; nếu eTroy hỗ trợ RP-initiated logout (end_session_endpoint) thì chuyển hướng để kết thúc phiên ở eTroy.
  • SPK-02 kiểm tra với repo eTroy_OIDC trước M1: claim có sẵn, hạn token, refresh token, logout, chữ ký (thuật toán), môi trường thử nghiệm cho staging (ASM-13).

8.9. Adapter giả lập cho kiểm thử

  • FakeModelGateway (Python) và chế độ “fake” của agent-core cho service TypeScript dùng trong test tích hợp: trả kịch bản ghi sẵn theo (agent, bước), tiêm lỗi theo mã chuẩn, đếm attempts — dùng cho test domain chạy không mạng (NFR-MAINT-004) và kiểm thử chấp nhận ngoài 19.10 (DEC-40).
  • RecordedModelGateway: phát lại phản hồi thật đã ghi (cassette) để test hồi quy rẻ; cassette không chứa key.
  • FakeSourceAdapter, FakeOidcProvider (phát ID token ký bằng khóa test), object storage MinIO, LocalKms, RabbitMQ trong Testcontainers — trong libs/ts/testing và sires_common.
  • Môi trường dev chạy đủ luồng với adapter giả lập; staging dùng provider thật bằng key của đội phát triển.
