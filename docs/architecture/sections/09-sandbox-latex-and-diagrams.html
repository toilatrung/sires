9. Sandbox: LaTeX and Diagrams

Trạng thái: bản 0.2 — ADR-11 Accepted; controller viết bằng NestJS · Cơ sở: PRD 12, 13, 17.4–17.5, NFR-SANDBOX-001, NFR-PERF-007; ASM-07, ASM-08; ADR-11

Bài toán: chạy mã do người dùng và agent viết (TeX là ngôn ngữ Turing-complete; Mermaid chạy trong trình duyệt headless) mà không cho đọc file hệ thống, gọi mạng, chạy lệnh shell hay chiếm tài nguyên; đồng thời build phải bắt đầu trong ≤ 10 giây (NFR-PERF-007) và cho kết quả tái lập được. Phương án: pool container cô lập khởi động sẵn, chạy dưới gVisor, không mạng, mỗi job một workspace tạm, image cố định phiên bản.

9.1. Mô hình sandbox

manuscript ──[TX] Build Queued──► queue sandbox.build ──► sandbox-runner controller (NestJS, ngoài sandbox, quyền S3 hạn chế)
                                            │ 1 tải file của revision từ object storage
                                            │ 2 ghi vào thư mục tạm, mount read-write duy nhất
                                            ▼
                                     sandbox container (gVisor, no network, non-root, read-only rootfs)
                                            │ latexmk / mmdc, giới hạn 120 s, 2 GB, CPU, PID, đĩa
                                            ▼
                                   controller đọc out.pdf, log → object storage → REST manuscript → [TX:manuscript] Build kết thúc
  • Container sandbox không có thông tin xác thực, không có quyền tới database hay object storage; chỉ thấy thư mục job. Mọi I/O với bên ngoài do controller làm; controller không có database, trạng thái Build nằm ở manuscript.
  • Mỗi job một thư mục mới; container được tái sử dụng trong pool nhưng thư mục bị xóa sau job; cứ sau N job (mặc định 50) hoặc khi có lỗi bất thường thì thay container mới.

Giới hạn 120 s / 2 GB là mặc định người vận hành cấu hình được (OQ-074); vượt giới hạn → Build Failed với mã timeout hoặc memory_limit và thông điệp rõ ràng.

9.3. Build LaTeX

  • Image: TeX Live một năm phát hành cố định (ghi phiên bản trong tên image), bộ package học thuật phổ biến (danh sách trong sandbox/latex/packages.txt), font cho XeLaTeX tiếng Việt và tiếng Anh. Đổi image = phát hành có kiểm thử với template Default và luận văn mẫu (ASM-07).
  • Lệnh: latexmk -pdf (pdfLaTeX) hoặc -xelatex, -interaction=nonstopmode -halt-on-error -file-line-error -no-shell-escape; BibTeX + natbib; references.bib được System sinh lại từ Trusted Reference trước khi tải vào workspace (MS-BIB).
  • Phân tích log: bộ phân tích trong controller trích lỗi/cảnh báo dạng (file, dòng, mã, thông điệp gốc) và ánh xạ sang mã thân thiện (missing_package, undefined_citation, missing_file, syntax_error…) để client hiển thị song ngữ (INT-LATEX-004). Đồng thời trích citation key thấy được và key không phân giải cho KPI-02.
  • Bộ nhớ đệm: lưu PDF theo hash của tập file đầu vào + phiên bản image + compiler; build lại cùng revision trả ngay kết quả cũ (không tốn sandbox).
  • Kết quả: log đầy đủ và PDF vào object storage; Build ghi issues[], citationKeysFound[], unresolvedKeys[] (INT-LATEX-003).

9.4. Kiểm tra và render Mermaid

  • Kiểm tra cú pháp (INT-DIAGRAM-001): chạy mermaid.parse trong một tiến trình Node trong sandbox; lỗi trả về kèm dòng. Đây là thao tác nhanh (< 1 s), dùng làm tool của Diagram Agent trong vòng tool calling.
  • Render (INT-DIAGRAM-002): mmdc (mermaid-cli, Chromium headless) → SVG; cấu hình puppeteer chặn mọi request mạng; theme cố định phù hợp in ấn.
  • Phân loại lỗi (INT-DIAGRAM-004): lỗi ở parse = lỗi cú pháp; parse đạt nhưng render lỗi/hết giờ = lỗi render.
  • Xuất cho LaTeX (INT-DIAGRAM-003, OQ-060): SVG → PDF vector bằng rsvg-convert; lỗi thì PNG 300 dpi qua Chromium screenshot và ghi cảnh báo vào Change Proposal.
  • Tool do Diagram Agent gọi trong Agent Run đi qua research, được gửi vào sandbox.build với độ ưu tiên cao (priority queue của RabbitMQ), chờ kết quả đồng bộ (timeout 30 s cho parse, 120 s cho render).

9.5. Hàng đợi và dung lượng

  • NFR-PERF-007 (Queued → Running ≤ 10 s, p95) cần container sẵn sàng: pool tối thiểu 2 sandbox LaTeX và 1 sandbox Mermaid luôn chạy; autoscaler (KEDA theo độ sâu queue sandbox.build của RabbitMQ) thêm pod khi hàng đợi > 0 quá 5 giây. Cold start của pod gVisor phải đo ở SPK-06.
  • Ưu tiên trong hàng đợi build: parse Mermaid > build do người dùng bấm > build tự động sau chấp nhận Change Proposal.
  • Giới hạn công bằng: tối đa 2 build đồng thời mỗi tài khoản; build mới cho cùng manuscript hủy build cũ đang Queued (chỉ build revision mới nhất).
  • Ước lượng: 100 tài khoản hoạt động, mỗi tài khoản trung bình 1 build/5 phút khi viết, build 20–60 s → khoảng 4–8 sandbox đồng thời lúc cao điểm.
