PH-01. Nền tảng chung, spike và hợp đồng baseline

Mục tiêu: sau giai đoạn này mọi luồng viết được logic nghiệp vụ trong thư mục của mình mà không phải chờ hay sửa mã của luồng khác.

  • platform: thư viện TS và Python cho tenancy (RLS), transaction, outbox + relay, inbox, idempotency, audit-emit, problem+json, OpenTelemetry, logger che dữ liệu, service-auth guard, UUIDv7; libs/ts/testing với Testcontainers (PostgreSQL 16 + pgvector, RabbitMQ, MinIO), FakeOidcProvider, fake broker, FakeSourceAdapter, LocalKms; sires_common với FakeModelGateway có hành vi xác định (kiến trúc 8.9; OQ-095: kịch bản ngoài 19.10 dùng provider giả lập).
  • contracts: sinh type TS từ OpenAPI công khai, nội bộ và AsyncAPI; sinh client Python từ OpenAPI nội bộ và mô hình message từ AsyncAPI (kiến trúc 2.4); kiểm tra code lệch spec trong CI (ADR-14).
  • infra: bổ sung CI: contract test (Schemathesis), kiểm tra payload theo AsyncAPI, redocly lint khi sửa spec, quét phụ thuộc và secret, build image; Nx remote cache; module Terraform; dựng staging khi có trả lời AQ-12.
  • Mỗi luồng service: migration database của mình từ docs/database/ddl, chạy trên PostgreSQL 16 + pgvector, đưa test hành vi DDL vào CI; cấu hình, service token, khung module (1.6); README ghi entity sở hữu và bản sao chỉ đọc.
  • web: shell (routing theo IA PRD 4, token Cream, i18n vi/en, client API, client SSE, trạng thái loading/empty/error dùng chung), mock theo OpenAPI cho các khu vực.
  • Spike do luồng sở hữu chạy: SPK-01, SPK-08 (agent-core, SPK-08 cùng orchestration), SPK-02 (gateway), SPK-03 (library), SPK-04, SPK-05 (knowledge), SPK-06, SPK-07 (sandbox-runner), SPK-10 (platform, infra). SPK-09 cần engine nên chạy ở PH-03; SPK-11 cần phiên thảo luận nên chạy ở PH-04.

Cổng ra PH-01:

  1. Một service mẫu dùng thư viện platform: ghi trạng thái + Audit Event + outbox trong một giao dịch; consumer xử lý sự kiện đến trùng đúng một lần; RLS chặn đọc chéo tài khoản. Có test cho cả ba.
  2. Pull request chạm một service NestJS chạy CI dưới 10 phút (SPK-10, kiến trúc 11.3).
  3. Hợp đồng baseline: DBQ-03, DBQ-04 đã sửa vào docs/api-design; type sinh không lỗi; người duyệt theo OQ-103 duyệt baseline.
  4. Báo cáo SPK-01–SPK-08, SPK-10. Giả định nào bị bác bỏ thì ADR, OQ hoặc AQ tương ứng được cập nhật trước khi vào PH-02.
  5. AQ-12 (nhà cloud, vùng dữ liệu) có trả lời. Nếu chưa, PH-02 không có staging và cổng PH-02 không kiểm được.

PH-02. Lát 1 — Truy cập, lệnh ghi và realtime

Hội tụ: web (shell, settings, global: Projects, khung Dashboard), gateway, identity, workspace, audit, agent-core (chỉ endpoint kiểm tra kết nối provider). Luồng F-01 (đăng nhập eTroy OIDC), F-02 (lệnh ghi chuẩn), F-03 (realtime qua SSE).

  • Requirement trọng tâm: INT-OIDC-001–004, NFR-AUTH, NFR-SECRETS-001–003 (envelope encryption API key), AGENT-PROVIDER, WS-*, PROJ-* (tạo, lưu trữ, xóa mềm 30 ngày), mục 15.12.
  • Staging chạy lần đầu: merge vào main tự deploy service thay đổi, chạy migration của service đó, smoke Playwright (kiến trúc 11.3). Từ đây staging cập nhật liên tục để lần deploy production không phải lần đầu.
  • Điều kiện ngoài: eTroy OIDC môi trường thử và client SIRes đã đăng ký (SPK-02); xác nhận RP-initiated logout chấp nhận post_logout_redirect_uri của SIRes (ETR-07, cần trước khi tích hợp đăng nhập); AQ-12.

Cổng ra PH-02: TS-12-07 (đăng nhập, đăng xuất) đạt trên staging; phiên hết hạn sau 12 giờ không hoạt động (INT-OIDC-003-AC02); tạo, lưu trữ, xóa mềm project; lưu và kiểm tra Provider Connection, key không xuất hiện trong log hay phản hồi (một phần REL-07); sự kiện từ outbox tới web qua SSE; tài khoản B không đọc được project của A (một phần REL-05, TS-12-01).

PH-03. Lát 2 — Chat, workflow engine và Agent Run

Hội tụ: orchestration (module engine, prompts, usage), agent-core (Model Gateway ba provider, registry, Context Assembler, Orchestrator), workspace (Conversation, Message, PendingAction, Notification), identity (giao ProviderSecretEnvelope cho Agent Run), gateway (stream chat.delta, SSE trạng thái workflow), audit, web (project: Overview, Chat; monitoring: Activity, Workflow, AgentList; global: PendingActions, Notifications). Luồng F-04, F-07, F-08, F-12.

  • Engine: bước tuần tự, checkpoint, heartbeat 30 s / 2 phút, sweeper, Recovery decision, Waiting for User ↔ Paused (DEC-53), thử lại hai lớp (8.5, 17.1).
  • Prompt và phê duyệt: chỉ Researcher thực hiện APR-01–APR-10; agent gửi lệnh “approve” bị từ chối và ghi Audit Event.
  • SPK-09 bản đầu: dừng orchestration, agent-core, consumer, RabbitMQ ở từng bước; đo khôi phục (TR-01 cần làm sớm).

Cổng ra PH-03: chat với Orchestrator có stream; Agent Run chạy được với từng provider Claude, OpenAI, Gemini (staging dùng key của đội, DEC-40); TS-02-05 và TS-05-05 đạt (một phần REL-04); workflow tiếp tục đúng sau khi dừng agent-core giữa bước; usage ghi theo Agent Run.

PH-04. Lát 3 — Plan, Task và phiên thảo luận

Hội tụ: planning (Research Plan, Plan Version, Phase, Task, TaskDefinition, dependency, readiness, TaskReview, phân tích ảnh hưởng), orchestration (StepPlan, bước song song, saga áp dụng đầu ra, module deliberation), agent-core (Orchestrator lập Plan, Analysis Agent A, B), identity (danh mục capability cho readiness), library (endpoint nội bộ phục vụ readiness: reference đã chọn của project), web (planning; tab Thảo luận ở monitoring; thẻ đề xuất thảo luận ở Chat). Luồng F-05, F-06, F-13; WF-01, WF-02, WF-03.

  • Phiên thảo luận theo DEC-47, DEC-48: đúng 2 Analysis Agent, Vòng 1 ẩn lập trường, Vòng 2 phản biện chéo, Orchestrator tổng hợp giữ bất đồng; Deliberation Board chỉ ghi thêm; Context Snapshot; nhãn deliberated/skipped.
  • SPK-11: chi phí, độ trễ, tải ghi của một phiên (3 bên, 2 vòng) với ba provider (TR-10).
  • library chỉ cần hội tụ phần readiness ở lát này; Discovery và nhập reference hội tụ ở PH-05.

Cổng ra PH-04: kịch bản TS của WF-01, WF-02, WF-03 ở PRD 19 đạt với provider giả lập; Plan Version Proposed → Approved chỉ bằng thao tác của Researcher; Task bị chặn khi readiness thiếu đầu vào; một phiên thảo luận hai vòng chạy hết và được khôi phục sau gián đoạn.

PH-05. Lát 4 — Discovery, Trusted Library và index tài liệu

Hội tụ: library (adapter Scholar trung gian, OpenAlex, Semantic Scholar có rate limiter; DOI qua Crossref, DataCite; BibTeX, RIS; tải PDF; duyệt reference theo lô; ProjectReferenceSelection), knowledge (trích xuất PDF, chunk, embedding bằng key của người dùng, pgvector, truy xuất lai), agent-core (Discovery, Reference Processing), orchestration (bước của WF-04), web (library: Discover, Library, Reference). Luồng F-09; WF-04.

  • Điều kiện ngoài: hợp đồng với dịch vụ trung gian Google Scholar (DEC-19), chọn theo kết quả SPK-03. Chưa có hợp đồng thì lát chạy với nguồn dự phòng OpenAlex, Semantic Scholar và nhập thủ công.
  • Phụ thuộc: lát này cần lát 2; chỉ Discovery Agent chạy trong một Task mới cần lát 3. Kế hoạch hiện xếp sau PH-04; có cho chồng hai giai đoạn không là OQ-106.

Cổng ra PH-05: kịch bản WF-04 đạt; PDF có lớp văn bản ≤ 50 MB được index; truy xuất có lọc trên 500 reference đạt p95 ≤ 3 s (NFR-PERF-006, SPK-04); reference bị thu hồi phát sự kiện tới các service có bản sao.

PH-06. Lát 5 — Evidence, kiểm chứng, bản thảo và sơ đồ

Hội tụ: research (Evidence, Claim, ClaimEvidenceLink, VerificationResult, Artifact, ArtifactVersion, registry đầu ra), knowledge (truy xuất cho evidence), manuscript (Manuscript, ManuscriptFile, ManuscriptRevision, ChangeProposal, BibliographyEntry, Build, cổng citation), sandbox-runner (image TeX Live, mermaid-cli, gVisor không mạng, pool), agent-core (Evidence Retrieval, Synthesis, Writing, Verification, Diagram), audit (KPI định kỳ, export JSON/CSV), eval (harness, baseline, cổng hồi quy trong CI), infra (node pool sandbox), web (research, manuscript). Luồng F-10, F-11; WF-05, WF-07.

  • Điều kiện ngoài: bộ dữ liệu nghiệm thu (5 đề tài, 3 lĩnh vực, khoảng 30 reference và 100 claim mỗi đề tài; nhãn chuyên gia; nhãn evidence cho 1 đề tài) do PO chuẩn bị, QA đưa vào (19.14, DEC-45). Cần có khi bắt đầu PH-06 để chạy baseline eval; bắt buộc trước PH-07.
  • Từ giai đoạn này, thay đổi thuộc danh sách NFR-EVAL-004 chạy eval harness và bị chặn khi vượt dung sai 2 điểm phần trăm (DEC-45).

Cổng ra PH-06: kịch bản WF-05, WF-07 đạt; bản thảo compile thành PDF trong sandbox; Change Proposal có citation lỗi bị chặn ở cổng citation; baseline eval đầu tiên được duyệt và lưu ở eval/baselines; KPI-01, KPI-02 đo được trên bộ dữ liệu nghiệm thu.

PH-07. Ổn định và nghiệm thu phát hành

Mọi luồng chỉ sửa lỗi, hoàn thiện requirement còn lại và tăng độ bền; không thêm tính năng ngoài PRD. Phạm vi P1 cần xong trước phát hành là OQ-104.

  • SPK-09 đầy đủ: fault injection ở mọi bước, đo KPI-03 ≥ 99%.
  • Kiểm thử tải k6 trên dữ liệu mẫu 16.4: 100 tài khoản đồng thời, mỗi tài khoản ≥ 3 workflow (NFR-SCALE-003).
  • Bảo mật: review nội bộ và quét tự động (AQ-04); kịch bản 19.12 cho REL-04, REL-05; rà API key cho REL-07 (TS-10-07).
  • Giao diện: rà toàn bộ màn ở hai ngôn ngữ (REL-08), trạng thái và khả năng tiếp cận (TS-13-06), skill sires-ui-review.
  • Vận hành: purge, retention, export; diễn tập khôi phục PITR theo từng database; cảnh báo đầy đủ (kiến trúc 11.4); runbook (11.6).
  • Nghiệm thu: REL-01 trên staging; REL-02 do PO thực hiện đề tài mẫu qua ít nhất hai phiên; REL-03, REL-06, REL-10 với provider thật trên bộ dữ liệu nghiệm thu (đội phát triển chịu chi phí, OQ-095); REL-09 danh sách lỗi.

Cổng ra PH-07: báo cáo REL-01–REL-10 đạt; PO ký chấp nhận phát hành (19.14).

PH-08. Triển khai production

  • Dựng production bằng cùng module Terraform và Helm chart đã dùng cho staging (kiến trúc 11.2): Kubernetes managed nhiều zone, PostgreSQL HA có PITR, RabbitMQ 3 node quorum, object storage, KMS, secret manager, CDN + WAF, egress NAT cố định.
  • Đăng ký client production với eTroy OIDC, kiểm tra RP-initiated logout (ETR-07).
  • Thứ tự lần deploy đầu: hạ tầng → migration của từng database → service backend → gateway → web lên CDN. Production cần phê duyệt thủ công, rolling update từng service, rollback bằng image trước (11.3).
  • Smoke test production (đăng nhập, tạo project, chat); synthetic check uptime; cảnh báo bật; lịch trực và kênh báo sự cố.
  • Theo dõi sau phát hành: thời lượng và tiêu chí kết thúc chốt khi chia việc.
  • Phát hành rộng (nếu khác phát hành đầu, OQ-105) cần thêm: một lần kiểm thử xâm nhập độc lập (AQ-04) và back-channel logout của eTroy One (ETR-07).

Cổng ra PH-08: production chạy với người dùng thật; smoke đạt; observability và cảnh báo hoạt động; runbook sẵn sàng; PO xác nhận go-live.

2.9. Quy tắc chung cho mọi cổng

  • Cổng kiểm trên staging (PH-02 trở đi), không kiểm trên máy cá nhân.
  • Requirement được tính xong theo Definition of Done ở PRD 19.14: AC có test và đạt, code truy vết về requirement ID, chuyển trạng thái đúng bảng mục 18, kiểm tra quyền có test cả trường hợp bị từ chối, Audit Event có actor, giao diện đủ loading/empty/error và song ngữ.
  • Luồng chưa đạt cổng không chặn luồng khác tiếp tục xây trong cô lập; chỉ chặn việc kiểm cổng của giai đoạn sau có dùng lát đó.
  • Kết quả mỗi cổng ghi vào nhật ký docs/docs_context.md khi PO xác nhận.
