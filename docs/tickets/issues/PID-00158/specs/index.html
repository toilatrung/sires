4. Thiết kế kỹ thuật

4.1. Dữ liệu

  • Không tạo bảng, không đổi DDL. SQL sinh ra chỉ chạm app.state_transition, chỉ các dòng có machine thuộc danh sách truyền vào.
  • Dòng: mỗi cặp khai báo là một dòng (machine, from_state, to_state, code); code không khai báo → NULL. Dòng sắp theo machine, rồi from_state, rồi to_state, so theo code point Unicode (TS không dùng localeCompare; Python so chuỗi mặc định). Thứ tự khai báo không ảnh hưởng đầu ra.
  • SQL đồng bộ (renderStateTransitionSql), theo thứ tự:
    1. Hai dòng chú thích cố định: câu nói SQL sinh từ khai báo state machine, không sửa tay (DR-01, DEC-57); câu liệt kê machine kèm số cặp theo thứ tự đã sắp.
    2. Câu DELETE FROM app.state_transition WHERE machine IN (…) AND (machine, from_state, to_state) NOT IN (VALUES …); — xóa cặp không còn trong khai báo của các machine đó.
    3. Một dòng --> statement-breakpoint (dấu tách câu của drizzle-kit; với PostgreSQL là chú thích).
    4. Câu INSERT INTO app.state_transition (machine, from_state, to_state, code) VALUES … ON CONFLICT (machine, from_state, to_state) DO UPDATE SET code = EXCLUDED.code WHERE app.state_transition.code IS DISTINCT FROM EXCLUDED.code;
    Xuống dòng luôn là LF; kết thúc bằng một LF. Chuỗi bọc nháy đơn, nháy đơn bên trong nhân đôi; không dùng E'' hay $$. Không có thời gian, đường dẫn, phiên bản hay giá trị phụ thuộc máy. Dạng chữ chính xác (thụt lề, mỗi dòng VALUES một cặp) do Dev chọn ở S02 và được ghim bằng golden.txt; Python phải cho đúng chuỗi đó.
  • Từng câu (stateTransitionStatements): trả hai câu DELETE, INSERT ở trên (không chú thích, không dấu tách) để chạy riêng từng câu — Alembic op.execute trên asyncpg không chạy nhiều câu trong một lệnh có chuẩn bị (EC19).
  • Bộ mẫu dùng chung golden-machines.json: mảng khai báo dạng dữ liệu (khóa machine, states, transitions với from, to, code, actors). Phải có: ít nhất hai machine; cặp có mã và không mã; trạng thái có khoảng trắng; một giá trị có nháy đơn; một giá trị không phải ASCII (EC07, EC08). golden.txt là đầu ra mong đợi; file .txt nên add-license.mjs không chèn giấy phép vào.

4.4. Quy tắc và trạng thái

  • Khai báo của service là nguồn duy nhất của state machine (NFR-MAINT-003, DEC-57). Thư viện không chứa machine của service nào; dữ liệu mẫu chỉ ở testdata.
  • Hàm kiểm chỉ xét cặp (từ, đến). Guard, chọn đích (ví dụ T-10 về Ready hay Blocked), quyền theo trạng thái, APR, actor được phép và Audit Event thuộc module domain của service (database 10.2). Helper không đọc database, không gọi mạng (NFR-MAINT-004).
  • Cặp X → X không được khai báo và luôn bị hàm kiểm từ chối; database không tra cặp này vì trigger bỏ qua UPDATE giữ nguyên trạng thái.
  • Dùng trong migration (ghi ở README, H2, H4): (1) PID migration khai báo machine của service trong module domain và xuất danh sách (stateMachines / STATE_MACHINES); (2) build service rồi chạy lệnh in SQL; (3) tạo custom migration bằng drizzle-kit generate --custom hay revision Alembic, dán SQL (Alembic: lặp op.execute trên state_transition_statements); (4) node scripts/docs/add-license.mjs gắn giấy phép cho file .sql mới; (5) test database của service, sau khi áp mọi migration: compareStateTransitionRows trả rỗng (DR-01 “test so khớp trong CI”).
  • Đổi khai báo về sau: không sửa migration cũ; thêm migration mới chứa SQL sinh lại cho machine đổi, cùng migration sửa CHECK nếu thêm trạng thái (database 12.4). Migration không import khai báo lúc chạy: nội dung migration phải cố định (kiến trúc 6.10).
  • Tương thích ngược (quy tắc 1.4.5): chỉ thêm export; không đổi bootstrapService, HealthModule và module Python hiện có.
