Bản tóm tắt theo spec-read-skill. Lô làm rõ 17/11/2026 không có câu trả lời H của PO. Ngày 18/11/2026 PO chấp nhận mọi đề xuất của phiếu I1–I3 (H1–H3) và sáu quyết định chung D1–D6 (H4–H9, trang ticket mục 5); các quyết định đã gộp vào quy tắc dưới đây. Mỗi dòng dẫn nguồn.

Làm gì

Dựng database sires_orchestration bằng migration của service sao cho schema giống hệt DDL tham chiếu (00-common.sql rồi orchestration.sql), khai báo bảy state machine của orchestration dạng dữ liệu để sinh dòng app.state_transition bằng helper của PID-00158, kiểm hành vi DDL trên database dựng từ migration, cho Job migration (PID-00010) một lệnh chạy được trong image, và tách sẵn khung năm module con của orchestration để các PID sau (engine, prompt, context store, deliberation, usage) làm song song mà không đụng file của nhau. Không có API, sự kiện hay logic nghiệp vụ. Tác nhân: System (Job migration chạy trước mỗi lần deploy, PID-00010) và Dev của các PID sau.

Quy tắc

  • Migration theo service, chỉ tiến; drizzle-kit cho service NestJS; migration của một service không chạm database của service khác — kiến trúc 6.10
  • Quy ước migration (D1, H4): migration đầu là SQL chép từ orchestration.sql cùng đối tượng chung của 00-common.sql, đặt làm custom migration SQL của drizzle-kit (có journal), chạy bằng migrate() của drizzle-orm; mỗi service có lệnh migrate riêng và giá trị Helm migration.enabled, migration.command; schema Drizzle bằng TypeScript do PID tính năng viết — kiến trúc 6.10 (PO chốt 18/11/2026)
  • Image production không có drizzle-kit: Job migration chạy migration.command trước Deployment, lệnh dùng migrate() của drizzle-orm có trong image — PID-00010 (S02, EC01); H3
  • drizzle-orm, drizzle-kit, node-postgres vào pnpm catalog do PID-00001 thêm (D5, H8); PID này không thêm dòng catalog — quy tắc 1.4.7
  • DDL tham chiếu là chuẩn thiết kế; migration thật phải sinh ra cùng schema; CI dựng một database từ migration, một từ ddl/, so bằng công cụ diff schema — DBD-02; database 12.4
  • Migration của orchestration tạo cả đối tượng của 00-common.sql: extension pgcrypto, unaccent, pg_trgm; schema app, replica; các hàm app.* (UUIDv7, tenant, kiểm ActorRef, provenance, tg_row_version, tg_immutable, tg_state_transition, tg_project_writable, enable_tenant_rls, grant_standard); cấu hình tìm kiếm app.sires_simple; bảng outbox, inbox, idempotency_key, job_lock, state_transition — đầu file docs/database/ddl/00-common.sql (“migration thật … phải sinh ra cùng schema này”); docs/database/README.md (thứ tự chạy)
  • Bảng của orchestration: 12 bảng nghiệp vụ và kỹ thuật (workflow, workflow_step, agent_run, agent_run_debug_transcript, checkpoint, interactive_agent_prompt, context_item, context_snapshot, deliberation, deliberation_participant, deliberation_entry, usage_ledger) và bản sao replica.project_state qua app.create_replica_project_state() — docs/database/ddl/orchestration.sql; database 3.5
  • Bốn vai trò sires_orchestration_owner, _app, _system, _purge do hạ tầng tạo trước; migration đăng nhập bằng vai trò migrator là thành viên của _owner, không tạo vai trò — database 3.2. Ở môi trường cục bộ, compose tạo vai trò (PID-00159, D4, H7); tới khi có, test tự tạo vai trò trong container
  • Bảng app.state_transition là bản sinh tự động từ khai báo state machine của module domain, không viết tay; trigger giữ làm lớp bảo vệ thứ hai — DEC-57, DBQ-09, database 10.2
  • PID này khai báo bảy machine dạng dữ liệu (các cặp từ → đến có trong DDL, không điều kiện chuyển) trong mã domain của orchestration — nơi khai báo duy nhất, PID-00046 và các PID module dùng lại; dòng app.state_transition sinh bằng helper TypeScript của PID-00158 (libs/ts/platform), PID này không tự viết bộ sinh SQL; SQL sinh ra vào migration — H1, D2 (H5); DR-01; NFR-MAINT-003
  • Bảy machine của orchestration, 43 cặp chuyển: workflow 16, workflow_step 11, agent_run 5, prompt 3, context_item 2, deliberation 3, deliberation_entry 3 — database 10.2; PRD 18.2 (gồm Waiting for User → Paused, DEC-53)
  • Migration lỗi không để lại schema nửa vời; index lớn tạo CONCURRENTLY ngoài giao dịch (migration đầu không có) — database 12.4
  • Test hành vi DDL thuộc PID migration (D3, H2, H6): bằng vai trò _app trên database dựng từ migration, kiểm các hành vi đã ghi trong chú thích DDL (chuyển trạng thái, một Workflow chưa kết thúc cho mỗi Task — DATA-IDEMP-002, bản ghi bất biến, RLS, chặn ghi khi project không Active) — tickets PH-01; database 12.4
  • Module con: engine (Workflow, Step, Checkpoint, heartbeat, sweeper, Recovery decision), prompts (InteractiveAgentPrompt, phê duyệt APR), context-store (ContextItem), deliberation (Deliberation, Board, Snapshot), usage. engine là lõi; module khác gọi engine qua interface trong service, không sửa trạng thái workflow trực tiếp — tickets 1.6
  • Không import mã hay đọc database của service khác — quy tắc 1.4; apps/orchestration/README.md
  • Bất biến SIRes (agent đề xuất, System kiểm soát, Researcher quyết định; provenance; cách ly theo project và task) không có hành vi mới ở ticket này; schema giữ nguyên các ràng buộc phục vụ chúng (app.is_actor_ref, RLS, tg_immutable, tg_agent_run_final) đúng như DDL.
