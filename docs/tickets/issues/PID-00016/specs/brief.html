Bản tóm tắt theo spec-read-skill. Làm rõ ngày 17/11/2026 trong lô PH-01 (phiếu I1–I5); ngày 18/11/2026 PO chấp nhận mọi đề xuất và sáu quyết định chung D1–D6, gộp thành H1–H7 ở trang ticket mục 5. Mỗi dòng dẫn nguồn.

Làm gì

System, luồng identity. Dựng database sires_identity bằng migration đúng DDL tham chiếu (kèm lệnh migrate, giá trị Helm, test hành vi DDL), khai báo hai state machine của identity để sinh dòng app.state_transition, và module envelope để API key của Provider Connection chỉ được lưu ở dạng mã hóa envelope: key mã hóa bằng DEK ngẫu nhiên (AES-256-GCM), DEK được bọc bằng KEK nằm trong KMS. Khi chạy trên máy Dev dùng KMS cục bộ đọc KEK từ cấu hình. Identity chỉ mã hóa; giải mã thuộc agent-core và knowledge. API Provider Connection (PID-00042), giao envelope cho Agent Run (PID-00062), xoay KEK (PID-00137) không thuộc ticket này.

Quy tắc

  • Lưu: key rõ → DEK ngẫu nhiên (AES-256-GCM, AAD = accountId|connectionId) → ciphertext, tag GCM 16 byte nối cuối ciphertext; DEK → KMS Encrypt bằng KEK sires-provider-keys → wrapped DEK; ghi app.provider_secret (connection_id, account_id, ciphertext, nonce 12 byte, wrapped_dek, kek_version = id khóa KMS đã bọc DEK) — kiến trúc 10.3, docs/database/ddl/identity.sql, H4
  • KEK không rời KMS; identity chỉ có quyền Encrypt, agent-core và knowledge có quyền Decrypt; identity, gateway và client không bao giờ thấy lại key. Mã của identity không có hàm giải mã; giải mã chỉ có trong test để kiểm — ADR-10, kiến trúc 10.3, NFR-SECRETS-002, H2
  • app.provider_secret: vai trò _app chỉ INSERT, DELETE (không SELECT, không UPDATE); _system đọc cho API nội bộ; không vai trò nào UPDATE — DDL, database 4.1
  • Không log key: logger che chuỗi giống key (tiền tố của ba provider, chuỗi entropy cao) và trường tên api_key, authorization; ngoại lệ được chuẩn hóa trước khi ghi lỗi; key không có trong thông báo lỗi — kiến trúc 10.3, NFR-SECRETS-001, logger của PID-00001
  • KMS không truy cập được → lỗi rõ ràng, không lưu key dạng rõ — spec mục 4.7
  • KMS cục bộ (máy Dev): KEK 32 byte và id khóa đọc từ cấu hình (biến môi trường, .env cục bộ không commit); bọc DEK bằng AES-256-GCM, wrapped DEK = nonce 12 byte rồi ciphertext có tag 16 byte — đúng định dạng encrypt của sires_common.testing.LocalKms, không đặt AAD (kiến trúc 10.3 không có AAD ở bước KMS Encrypt), để phía Python mở được bằng cùng KEK; kek_version = id khóa trong cấu hình; thiếu cấu hình thì identity không khởi động; cùng cấu hình thì wrapped DEK cũ vẫn mở được sau khởi động lại — H1, H4
  • Envelope trả cho agent-core, knowledge sau này có ciphertext, nonce, wrappedDek (base64), kekKeyId (= kek_version), aad (chuỗi accountId|connectionId); không có trường tag riêng — docs/api-design/internal/schemas.yaml#/ProviderSecretEnvelope, H4
  • Migration theo kiến trúc 6.10 (PO chốt 18/11/2026): migration đầu là SQL chép từ identity.sql cùng phần chung của 00-common.sql, đặt làm custom migration SQL của drizzle-kit (có journal), chạy bằng migrate() của drizzle-orm qua lệnh migrate của service; chỉ tiến; schema Drizzle bằng TypeScript không thuộc migration. PID gồm test hành vi DDL, lệnh migrate và giá trị Helm migration.enabled, migration.command. Lệch DDL thì ghi DBQ, không tự đổi — DEC-57, DBD-02, kiến trúc 6.10, H5, H6
  • Dòng app.state_transition là bản sinh từ khai báo state machine dạng dữ liệu trong module domain của identity, không viết tay: account (cột status, 4 chuyển) và provider_connection (cột test_status, 6 chuyển), đúng các cặp trong DDL; sinh bằng helper của PID-00158; trigger chuyển trạng thái giữ SQL chép từ DDL; PID-00041, PID-00042 dùng lại khai báo — DR-01, DBQ-09, database 10.2, H3 (D2)
  • Vai trò sires_identity_owner, _app, _system, _purge không nằm trong migration: Terraform tạo ở staging, production; compose tạo ở máy Dev (PID-00159); tới khi có, test tự tạo vai trò cần dùng — database 3.2, H6 (D4)
  • Mọi bảng có account_id bật và ép RLS; app.account.account_id sinh từ id — DDL, 00-common.sql

Thuật ngữ

  • KEK = khóa bọc trong KMS (sires-provider-keys); DEK = khóa dữ liệu ngẫu nhiên cho mỗi lần lưu; wrapped DEK = DEK đã bọc bằng KEK.
  • kek_version (cột DDL) ↔ kekKeyId (trường hợp đồng): cùng một giá trị, là id khóa KMS đã bọc DEK (KMS cục bộ: id khóa trong cấu hình; KMS thật: id hoặc tên phiên bản khóa KMS trả về) — H4.
  • API key = khóa provider của Researcher trong Provider Connection (PRD 1.5, SCOPE-13).
